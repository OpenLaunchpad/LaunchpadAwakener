摘要

注入版 LaunchpadAwakener 与独立版 Launchpad 各自接上 Sparkle 2，每天检查一次更新，有新版本时弹 Sparkle 的标准窗口、用户确认后安装；菜单里加「Check for Updates…」，设置里加「自动检查更新」开关。两个 App 各有一个更新源（appcast），都作为附件挂在每次的 GitHub Release 上，由 CI 在发布时生成并用 EdDSA 签名；独立版的 zip 从注入版包里取出、单独上传。两个 App 都是常驻后台的（菜单栏 App、收起后藏起来的全屏 App），所以定时检查到的更新先以「提醒」出现：注入版在菜单栏菜单里，独立版在 Dock 图标的角标与菜单里。注入版更新后第一次启动时，如果 Dock 里跑的还是旧 payload，自动重启一次 Dock；独立版被 Sparkle 重新打开时不盖住屏幕。

要你定

批准这份提案后开始实现

  1. 按本提案的方案与落地步骤实现？第 5 步生成正式密钥、设仓库 secret、给 AppRelease 打 1.3.0 时会再单独问一次。

方案

  1. 两个 App 都接 Sparkle，放进新模块 LaunchpadAwakenerUpdating：一个 ApplicationUpdater 包住 Sparkle 的标准 updater。
    • 更新源：注入版 https://github.com/OpenLaunchpad/LaunchpadAwakener/releases/latest/download/LaunchpadAwakenerAppcast.xml，独立版同一处的 LaunchpadAppcast.xml。latest 永远指向最新的正式版，不含预发布版。
    • SUEnableAutomaticChecks = YES：默认每天自动检查，不弹询问；设置里可以关。自动下载安装保持 Sparkle 的默认（关）。
    • 开发构建没有更新源，updater 不启动、更新菜单项不出现；带启动参数 -UpdateFeedURL <地址> 时才启动，专供测试机验证。开发构建用一把单独的测试密钥。
  2. 入口：两个 App 的 App 菜单在「About」下面加「Check for Updates…」；注入版菜单栏菜单（两套）在「Quit」上面加；独立版 Dock 菜单加。设置里加自动检查开关与「Updates」一行（版本号 + 「Check Now」）。
  3. 定时检查到更新时（温和提醒）：
    • 注入版：Sparkle 自己显示窗口；不在立即聚焦时（窗口在别的 App 后面，菜单栏 App 又没有 Dock 图标），菜单栏菜单顶上多一项「Install Update <版本>…」。用户看过窗口或会话结束就撤掉。
    • 独立版：从不让 Sparkle 自己显示定时检查的结果（App 平时藏着，界面开着时盖在一切之上）。改为 Dock 角标、Dock 菜单顶上的「Install Update <版本>…」、设置窗口里的新版本号；点了才收起界面、显示 Sparkle 窗口。
  4. 更新之后：
    • 注入版：记下上次启动的构建号；换了构建（Sparkle 更新、手动替换都算）时，在重连驻留 payload 之后若 hasStalePayload 为真，调一次 restartTargets()。SIP 开着时不会重启。被 Sparkle 重新打开时控制面板不弹出。
    • 独立版：被 Sparkle 重新打开时不盖住屏幕，等用户点 Dock 图标；手动打开的照旧显示。
  5. 发布：
    • AppRelease 1.3.0：sparkle-appcast 发布器把发布说明嵌进 appcast；公开 app_release_generate_appcast 给钩子生成第二个 App 的 feed。
    • Release.zsh：发布器加 sparkle-appcast，每次从空 feed 开始；release_notes_path='ReleaseNotes/{tag_version}.md'，打 tag 前写好。
    • release_after_product：取出 Launchpad.zip、装订公证票据、压成 Launchpad-<版本>-<构建号>.zip 加进产物。
    • release_deploy_appcast：生成 LaunchpadAppcast.xml，两个 feed 用 gh release upload --clobber 传到这次的 Release。
    • 「Embed Standalone Launchpad」先由内向外签 Sparkle 的嵌套代码；release_verify_export 加对应检查。
    • 正式 EdDSA 密钥：公钥进 Release 配置，私钥存成仓库 secret SPARKLE_PRIVATE_KEY，Release.yml 交给 APP_RELEASE_SPARKLE_PRIVATE_KEY。设之前先问用户。
  6. 文档：新写实现说明 Documentations/Internal/AutomaticUpdates.md；改项目 CLAUDE.md、两份实现说明与 README。

非目标

  • 不做 beta 通道、增量更新、分阶段推送、关键更新标记。
  • 不保留 feed 的版本历史：每次只有最新一版。
  • 不让注入版在更新后顺带替换已装的独立版。
  • 不为已装 1.1.1 及更早版本的用户做什么：手动换到第一个带 Sparkle 的版本后才开始自动更新。
  • 不改 daemon 与输入法辅助进程的换新机制；不发系统通知。

模块依赖

两个 App 经新模块 LaunchpadAwakenerUpdating 链接 Sparkle；payload、daemon、输入法辅助进程不链接它。

发布与更新的数据流

发布顺序固定为 tag → Release → appcast → 部署钩子，钩子运行时 Release 已经在了。App 只读最新正式版上的 feed。

详细设计

LaunchpadAwakenerUpdating 的接口 
@MainActor
@Observable
public final class ApplicationUpdater {
    public enum ScheduledUpdatePresentation: Sendable {
        /// Sparkle shows its window; when it shows it behind other apps, the app adds a reminder too.
        case shownBySparkle
        /// The app only reminds, and Sparkle's window shows once the user asks for it.
        case remindedByApplication
    }
    public struct PendingUpdate: Equatable, Sendable { public var displayVersion: String }

    public private(set) var isStarted: Bool
    public private(set) var canCheckForUpdates: Bool
    public private(set) var pendingUpdate: PendingUpdate?
    public var automaticallyChecksForUpdates: Bool { get set }

    public init(scheduledUpdatePresentation: ScheduledUpdatePresentation, bundle: Bundle = .main, defaults: UserDefaults = .standard)
    public func checkForUpdates()
    public func makeMenuItem() -> NSMenuItem
}

public struct UpdateFeedResolution: Sendable {
    public static func feedURL(infoDictionaryValue: String?, overrideValue: String?, allowsOverride: Bool) -> URL?
}

public struct UpdateReminder: Equatable, Sendable {
    public static func letsSparkleShow(_ presentation: ApplicationUpdater.ScheduledUpdatePresentation, immediateFocus: Bool) -> Bool
    public private(set) var pendingUpdate: ApplicationUpdater.PendingUpdate?
    public mutating func sparkleWillShow(_ displayVersion: String, isUserInitiated: Bool, isShownBySparkle: Bool, immediateFocus: Bool)
    public mutating func userSawUpdate()
    public mutating func sessionEnded()
}

public struct UpdateRelaunchRecord {
    public init(defaults: UserDefaults = .standard)
    public func noteRelaunch()
    /// Whether Sparkle relaunched the app to finish an update; reading it clears it.
    public func takeRelaunchNote() -> Bool
}
  • 内部持有一个 SPUStandardUpdaterController，startingUpdater 取更新源是否算得出；canCheckForUpdates 与 automaticallyChecksForUpdates 用 KVO 跟着 SPUUpdater。
  • 代理是一个私有的 NSObject 子类，把 Sparkle 的回调翻成 UpdateReminder 的事件。supportsGentleScheduledUpdateReminders 恒为真；是否让 Sparkle 显示由 letsSparkleShow 决定：.shownBySparkle 恒真，.remindedByApplication 恒假。
  • 非用户发起、且 Sparkle 不显示或不在立即聚焦时设 pendingUpdate；用户看过或会话结束时清掉。
  • checkForUpdates() 先 NSApp.activate() 再调 Sparkle；有待装更新时 Sparkle 直接显示它。
  • feedURLString(for:) 只在开发构建里返回 UpdateFeedURL 覆盖值；updaterWillRelaunchApplication(_:) 调 noteRelaunch()。

public enum DockRestartAfterUpdate {
    public static func isNeeded(isNewBuild: Bool, isInjectionAllowed: Bool, hasStalePayload: Bool) -> Bool
}

// runLaunchSequence(), after reconnectToResidentPayloads()
if DockRestartAfterUpdate.isNeeded(isNewBuild: isNewBuild, isInjectionAllowed: !isInjectionBlockedBySystemIntegrityProtection, hasStalePayload: injectionCoordinator.hasStalePayload) {
    #log(.info, "First launch of build \(build, privacy: .public) with an older payload in the Dock: restarting the Dock once")
    injectionCoordinator.restartTargets()
    return   // restartTargets() injects into the new Dock itself
}

测试机上的验证

非交互地走「下载后退出时安装」：开发机编两版开发构建（构建号不同），较新的压成 zip、用测试密钥签名，与 feed 一起拷到 MacBook，用 python3 -m http.server 在本机端口上提供；defaults write com.MxIris.LaunchpadAwakener.debug SUAutomaticallyUpdate -bool YES，带 -UpdateFeedURL http://127.0.0.1:<端口>/LaunchpadAwakenerAppcast.xml 打开较旧的一版，等下载完成后退出让 Sparkle 安装，再打开：核对版本号、日志里的「restarting the Dock once」、注入正常、daemon 没要求重新批准。独立版同样做一遍。点 Sparkle 窗口里的按钮属于交互操作，只在用户同意时做。

动机与调研

动机
  • 两个 App 都没有更新途径。1.0（2026-11-12）、1.1（2026-11-22）、1.1.1（2026-11-23）十一天发了三个版本，修的都是一用就会碰到的问题，到不了已装的人手里。
  • 独立版只装在注入版包里的 Launchpad.zip 里，已经装过的原样保留（StandaloneLaunchpadInstaller.install()）；手动换了注入版，独立版仍停在旧版，没有任何提示。
  • SIP 开着的用户主要用独立版，注入版不一定开着；只给注入版接更新，这些用户永远收不到更新。
  • 换了注入版，Dock 里的旧 payload 卸不掉，现在要用户自己点「Restart Dock」；自动更新之后再让用户补这一步，等于只做了一半。
现状代码
  • 注入版启动：ApplicationDelegate.applicationDidFinishLaunching(_:)（ApplicationDelegate.swift:68）建菜单与菜单栏项；SIP 开着时只弹控制面板；否则开自动注入、登记并换新输入法辅助进程、不是登录时启动就弹控制面板，最后 runLaunchSequence()：daemon → reconnectToResidentPayloads() → 自动注入 → .ready。
  • PayloadInjectionCoordinator.hasStalePayload（:340）按镜像 UUID 判旧；restartTargets()（:610）是「Restart Dock」的实现。
  • daemon 版本不一致自动重装、辅助进程可执行文件被换就结束它：整包替换时照常生效，不改。
  • 菜单：ApplicationMainMenu.make（SharedUI/ApplicationMainMenu.swift:16）、StatusItemController（两套条目）、独立版 applicationDockMenu(_:)（StandaloneLaunchpad.swift:183，只有「Settings…」）。
  • 设置：控制面板「General」节（:213、:223）；独立版 StandaloneSettings（快捷键、Open at Login）。
  • 独立版不是登录时启动就盖住整块屏幕；收起后 NSApp.hide(nil)，窗口层级 27。
  • 注入版有只含 LSUIElement 的 Info.plist，独立版没有 Info.plist 文件；都没开沙盒，都开着硬化运行时。
  • 「Embed Standalone Launchpad」只重签框架 Resources/*.bundle 与框架本身，不处理别的嵌套代码。
  • Release.zsh 用 AppRelease 1.0.0，只有 github-release 发布器，发布说明事后用 gh release edit 补。
上游能力
  • Sparkle 2.10.1（2026-10-25，SwiftPM 二进制 XCFramework）：SPUStandardUpdaterController；温和提醒的四个代理方法（后台 App 在 immediateFocus 为假时，标准窗口「立即显示，但在其他 App 后面」；用户主动检查总由 Sparkle 显示）；feedURLString(for:)、updater(_:willInstallUpdate:)、updaterWillRelaunchApplication(_:)；generate_appcast 认同名的 .md 发布说明，--embed-release-notes 强制嵌入；Info.plist 键 SUFeedURL、SUPublicEDKey、SUEnableAutomaticChecks、SUScheduledCheckInterval。
  • AppRelease 1.2.0：sparkle-appcast 发布器用 App 链接的 Sparkle 包里的 generate_appcast，只放这次的 zip，预发布版加 --channel beta，私钥来自 APP_RELEASE_SPARKLE_PRIVATE_KEY；发布顺序 tag → Release → appcast → 部署钩子；暂存目录只放 zip，发布说明进不了 appcast，钩子拿不到内部的 generate_appcast 路径与私钥文件；release_after_product 可以加产物。
  • LyricsX：同一个发布器生成单条目 feed，再由钩子插进两个仓库的 appcast.xml 推送；发布说明事先写在 ReleaseNotes/。
推测，待验证
  • zip 里的独立版能不能单独装订公证票据：第 5 步演练里验证；不行就由钩子单独提交公证。
  • 导出会不会重签 Sparkle 的嵌套代码：release_verify_export 的逐个 Mach-O 检查给出答案。
  • Sparkle 换掉整个注入版之后，后台任务管理会不会再要求批准 daemon：推测不会，测试机上验证。

替代方案

9 条，均已否
  • 只给注入版接更新、顺带替换独立版：用户否决；独立版会一直停在旧版。
  • feed 提交进仓库、经 raw 或 Pages 提供：每次往 main 推机器人提交、多触发一次 CI、和共用检出搅在一起；挂在 Release 附件上什么都不用提交。
  • feed 保留历史：要先下载上一版合并，latest 变动时会出错；Sparkle 只需要最新一条。
  • 不改 AppRelease，全在钩子里做：可行但只借发布器的钩子、绕开它的输出，还要猜引擎的内部变量；做进引擎别的项目也能用。
  • 独立版另开仓库或另一串 Release：两个 App 同版本同构建，分开只会对不上。
  • 默认静默自动安装：这个工具注入 Dock、装特权 daemon，更新前让用户看一眼更合适；愿意的用户在 Sparkle 窗口里勾选。
  • 系统通知提醒：要先要通知权限；角标与菜单项不需要。
  • 改菜单栏图标提醒：图标是状态指示，混进去会让「出问题」和「有更新」分不清。
  • 自己写更新器：Sparkle 都做好了。

影响

用户可见变化

  • App 菜单、注入版菜单栏菜单、独立版 Dock 菜单多「Check for Updates…」；有待装更新时变成「Install Update <版本>…」。
  • 控制面板「General」节与独立版设置窗口各多两行。
  • 有新版本时：注入版弹 Sparkle 窗口（在后面时菜单栏菜单里有提醒）；独立版 Dock 图标出现角标。
  • 注入版更新后 Dock 重启一次，新 payload 自动注入；独立版被 Sparkle 重新打开时不盖住屏幕。原有操作都不变。

可发现性

默认开启自动检查，不额外询问：这类工具的用户本来就要跟着 macOS 的 Dock 变化拿修复。菜单与设置里都有入口和开关。

数据与配置兼容

  • 新增 Sparkle 的 SU* 键，以及构建记录与重新打开记录各一个键，都在各自 App 的偏好域里，不碰布局库与已有设置。
  • 从没装过 Sparkle 的版本升上来，构建记录为空按「换了构建」算：Dock 里若是旧 payload 就重启一次，与手动点「Restart Dock」相同。
  • 装回旧版不受影响。

平台与最低版本

不变（macOS 15 起）；26 与 27 行为相同。

发布

  • 不需要新 entitlement；Sparkle 的 XPC 服务用不上但照样签名。
  • 公证多了 Sparkle 的嵌套代码，导出与嵌入阶段都要签好，release_verify_export 检查。
  • 每次发布多传一个独立版 zip 与两个 feed；发布说明改为打 tag 前写进 ReleaseNotes/<版本>.md；需要仓库 secret SPARKLE_PRIVATE_KEY。
  • 第一个带 Sparkle 的版本（预计 1.2）发出后，自动更新从下一个版本起才起作用。

落地步骤

  1. 提案入库：无代码变化。
  2. Sparkle 骨架与更新源：releaseBuildUsesTheBundledFeed、developmentBuildWithoutOverrideHasNoFeed、developmentBuildUsesTheOverrideFeed、releaseBuildIgnoresTheOverride、emptyFeedValueCountsAsNone；Release 构建的 Info.plist 里有三个 Sparkle 键（RunScript 核对）。
  3. 菜单入口与温和提醒：shownBySparkleLetsSparkleShowScheduledUpdates、remindedByApplicationNeverLetsSparkleShowScheduledUpdates、updateShownOutOfFocusLeavesAReminder、updateShownInFocusLeavesNoReminder、userInitiatedCheckLeavesNoReminder、reminderClearsWhenTheUserSeesTheUpdate、reminderClearsWhenTheSessionEnds、menuItemOffersTheWaitingUpdate、mainMenuPutsTheUpdateItemUnderAbout。
  4. 设置行：两版控制面板表单都有两行更新设置，开发构建没有更新源时没有；切换开关写回 automaticallyChecksForUpdates。
  5. 更新之后：firstRecordedLaunchCountsAsNewBuild、sameBuildIsNotNew、differentBuildIsNew、restartsTheDockOnceForANewBuildWithAStalePayload、doesNotRestartWithoutAStalePayload、doesNotRestartWhileInjectionIsBlocked、doesNotRestartForTheSameBuild、relaunchNoteIsReadOnce、standaloneStaysHiddenWhenRelaunchedForAnUpdate、standaloneStaysHiddenWhenLaunchedAtLogin、standaloneShowsWhenOpenedByTheUser。
  6. 发布：AppRelease 的测试覆盖发布说明进 appcast 与第二个 feed；手动跑一次 Release.yml 演练，产物里有独立版 zip，其中的独立版已装订票据、spctl 判为 Notarized；release_verify_export 对两个 App 的 Sparkle 嵌套代码都通过；CI 通过。
  7. 测试机验证与文档：MacBook 上走通两个 App 的下载、退出时安装、重新打开；注入版重启 Dock 一次且注入正常，daemon 没要求重新批准；文档登记完毕。
